# SmartCampusOS 架构决策记录（ADR）

> 记录本项目的关键架构决策：决策背景、选择、理由与代价，供后续演进与新人理解约束来源。
> 状态含义：**提议** → **已接受** → **已实施** / **已替代**。关联代码位置随实现同步更新。

---

## ADR-001：微服务 + 事件驱动，而非模块化单体

- **状态**：已实施
- **日期**：2026-08-01
- **决策**：后端按领域边界拆分为 7 个微服务（Identity / Edu / Dorm / Notice / Data / Push / File）+ 1 个 API 网关，服务间同步调用走 REST（经网关），异步联动走领域事件（MassTransit + RabbitMQ）。
- **背景**：PRD 覆盖教务、宿舍后勤、通知家校、数据可视化四大业务域 + 通用平台，目标单校 5000 人在线、私有化交付与后续多校区部署；业务域之间耦合点明确（分班影响宿舍、成绩影响通知等），适合按域拆分。
- **备选方案**：
  1. 模块化单体起步、按需拆分 —— 部署简单、演进成本低，但当前团队已按域明确边界，拆分会带来二次重构；
  2. 全同步调用的大单体 —— 峰值场景（选课 3000 并发写入）难以独立扩缩容。
- **理由**：域边界清晰、峰值场景需要独立扩缩容、按校私有化交付需要按模块裁剪部署。
- **代价/后果**：
  - 分布式一致性复杂度上升，跨服务状态依赖最终一致（事件 + 幂等去重）；
  - 基础设施依赖（RabbitMQ/Redis/每服务一库）增加运维成本；
  - 实施顺序风险：**当前仅 IdentityService 完整落地，其余 6 个服务为脚手架**（见 LLD v1.1 状态标注），需按业务优先级逐域补齐。
- **关联**：LLD §2.1/§2.3；`02-Backend/Host/src/SmartCampusOS.AppHost/Program.cs`（Aspire 编排 7 服务 + 7 个 MySQL 库 + Redis + RabbitMQ）。

## ADR-002：每服务独立数据库，禁止跨库 JOIN

- **状态**：已实施
- **日期**：2026-08-01
- **决策**：每个微服务一个独立 MySQL 数据库（identity_db / edu_db / dorm_db / notice_db / data_db / push_db / file_db），禁止跨库 JOIN；跨服务数据通过接口（同步）或事件同步（异步）获取，必要时冗余存储展示字段（快照）。
- **背景**：FreeSql 原生支持多库；LLD 明确"数据库按服务隔离"。若共享库，服务边界形同虚设，且后续按校拆分/迁移困难。
- **备选方案**：共享库 + 逻辑隔离 —— 联查方便，但破坏服务自治，任何表结构变更影响全部服务。
- **理由**：保证服务自治与独立演进；配合事件同步保证最终一致；符合私有化交付时按域裁剪的需求。
- **代价/后果**：
  - 聚合查询（如"家长看子女在校一览"）需跨服务拼装，由 NoticeService 订阅事件维护聚合快照（noti_child_digest）；
  - 表结构变更须同步考虑事件契约；
  - 当前 50 张表仅 identity_db 12 张已实现，其余 38 张随对应服务落地（见数据库设计文档状态标注）。
- **关联**：LLD §2.1/§2.3；数据库设计文档 §10（跨服务数据引用约定）。

## ADR-003：ORM 选型 FreeSql，而非 EF Core

- **状态**：已实施
- **日期**：2026-08-01
- **决策**：数据访问使用 **FreeSql**（第三方 ORM），每服务一个 `IFreeSql` 实例，CodeFirst 建表（`SyncStructure`）+ 幂等播种（DbSeeder）。
- **背景**：需要 CodeFirst 自动建表（私有化交付免手工初始化）、原生多库/读写分离支持、实体映射灵活（Domain 层零第三方依赖，用自定义 `[EntityTable]` 特性由 Aop 映射表名）。
- **备选方案**：
  1. EF Core —— 生态成熟、文档丰富，但多租户/多库场景配置繁琐，CodeFirst 迁移较重；
  2. Dapper —— 轻量但需手写大量 SQL，样板代码多。
- **理由**：FreeSql 与"每服务一库 + CodeFirst 自动建表 + 读写分离"目标匹配度最高；Domain 实体可保持纯净（无 ORM 特性依赖）。
- **代价/后果**：
  - FreeSql 为第三方小众 ORM，社区与招聘池相对小；
  - 需团队内沉淀使用约定（仓储只出现在 Infrastructure 层，见 LLD §2.6.4）。
- **关联**：LLD §2.4/§2.6.4；`IdentityService.Infrastructure/Persistence/FreeSqlFactory.cs`、`DatabaseInitializer.cs`。

## ADR-004：JWT 校验集中在 ApiGateway，服务信任 X-* 透传头

- **状态**：已实施
- **日期**：2026-08-01
- **决策**：JWT 签发/校验只在 ApiGateway 进行（HS256，白名单路径免鉴权）；网关校验通过后把用户上下文以 `X-User-Id`、`X-User-Roles`、`X-Data-Scope` 等请求头透传给下游服务；服务内仅通过 `ICurrentUser`（`HttpCurrentUser`）解析这些头，不再验签。登出/改密后令牌进 Redis 黑名单。
- **背景**：若每个服务各自验签，密钥管理与签名算法升级将逐服务铺开；且数据权限（DataScope）需在网关统一解析注入，才能保证各服务在仓储层一致过滤。
- **备选方案**：
  1. 各服务独立验签（API 层中间件）—— 密钥轮换/算法升级成本 ×N，且无法统一黑名单策略；
  2. 网关只转发不鉴权，服务内自鉴 —— 与"网关统一入口"原则冲突。
- **理由**：单一安全边界、统一限流与黑名单策略、服务无状态化（不持有密钥）；BDD 测试因此经真实网关验证契约（Reqnroll）。
- **代价/后果**：
  - 服务必须信任网关透传头 —— 内网须保证服务端口不对外暴露（当前服务端口 5111~5117 仅本机/Aspire 内部使用）；
  - X-* 头契约变更需网关与所有服务同步，靠契约/功能测试守护；
  - 网关成为单点 —— 需多副本部署（LLD §10.1，K8s 目标架构）。
- **关联**：LLD §3.1/§8；`ApiGateway/Middleware/JwtAuthenticationMiddleware.cs`、`Security/JwtTokenValidator.cs`；`IdentityService.Api/CurrentUser/HttpCurrentUser.cs`；SharedKernel `Users/ICurrentUser.cs`。

## ADR-005：跨服务异步联动走领域事件（MassTransit + RabbitMQ）

- **状态**：已接受（基础设施已装配，事件链路随各服务逐步启用）
- **日期**：2026-08-01
- **决策**：跨服务的状态联动（分班→宿舍、调课→通知、成绩→预警等）一律发布领域事件（`IntegrationEvent`，含 `eventId` 幂等去重），经 MassTransit + RabbitMQ 异步消费，最终一致；不直接跨服务同步调用业务接口。
- **背景**：同步调用链（如"成绩发布 → 通知家长 + 刷新指标"）会产生跨服务强耦合与故障传导；峰值场景需要削峰。
- **备选方案**：
  1. 全同步 HTTP 调用 —— 简单直接，但调用链脆弱、扩缩容互相牵制；
  2. 数据库 CDC —— 侵入性强，与多库隔离冲突。
- **理由**：事件驱动的最终一致性对"通知/统计"类非强一致场景足够；消息队列天然削峰（选课写入高峰）。
- **代价/后果**：
  - 需要幂等消费（`eventId` 去重）、死信与重试策略；
  - 事件 schema 演进需兼容（向后兼容字段新增）；
  - 当前仅 SharedKernel 事件基类与 IdentityService 装配完成，事件表（LLD §7）中多数消费方服务未落地。
- **关联**：LLD §2.5/§7；`SmartCampusOS.SharedKernel/Events/IntegrationEvent.cs`、`ServiceNames.cs`。
